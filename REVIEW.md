# REVIEW.md

Review of the starter `app/main.py`. Every row below was fixed in the final `app/main.py`.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `MongoClient(...)` (top) | Client is not `tz_aware`, so every datetime read from MongoDB is naive. Nothing says which zone a naive value is in, so arithmetic and conversions silently go wrong. | `punch_in - aware_datetime` raises `TypeError`; epoch conversion depends on the server's local zone. | `tz_aware=True`; all datetimes are aware UTC, converted to/from epoch ms in `ms_to_dt` / `dt_to_ms`. |
| 2 | `/health` | Returns `ok` without touching MongoDB, so it is 200 even when the database is down. The runner would start testing too early. | Stop MongoDB, call `/health`: still 200. | `ping` the database; `PyMongoError` -> 503. |
| 3 | Startup (no indexes anywhere) | No indexes. `emp_code` is not unique, `(emp_code, date)` is not unique, and every list/analytics query is a collection scan. | Two parallel `POST /employees` with the same code can both succeed; `/attendance` slows down with 100k rows. | `ensure_indexes()` at startup (idempotent): unique `emp_code`, unique `(emp_code, date)` and four query indexes. |
| 4 | `create_employee` | Check-then-insert race (`find_one`, then `insert_one`); two parallel creates both pass the check. No validation at all (any `emp_code`, bad email, `shift_start == shift_end`, `joined_on="banana"`). `created_at = datetime.now()` is naive local time and is returned as an ISO string, not epoch ms. | 10 parallel POSTs -> several 201s. `shift_start="25:99"` is accepted. | Validation in the pydantic model (patterns, lengths, real calendar date, shifts must differ); the unique index decides, `DuplicateKeyError` -> 409; `created_at` is UTC now, returned as epoch ms. |
| 5 | `list_employees` | `skip = page * page_size` skips the first page (off by one). `total` is `count_documents({})`, ignoring the department filter. No sort, so the order is arbitrary (contract: `emp_code` ascending). No bounds on `page` / `page_size` (`page=0` -> negative skip -> 500). | `page=1` never shows the first employees; `?department=Sales` shows the total of everybody. | `skip = (page-1)*page_size`, `count_documents(q)` with the same filter, `sort emp_code`, `page >= 1`, `1 <= page_size <= 100`. |
| 6 | `punch_in`: unknown employee | `emp` is `None` for an unknown `emp_code` and `emp["shift_start"]` raises `TypeError` -> 500. | `{"emp_code": "NOPE"}` | `get_employee()` raises 404 first. |
| 7 | `punch_in`: race | `find_one` then `insert_one`: two simultaneous punch-ins both pass the check and create two records for one day. | Fire 5 identical punch-ins in parallel; expect one 201 and four 409. | The unique `(emp_code, date)` index is the guard; `insert_one` and catch `DuplicateKeyError` -> 409. |
| 8 | `punch_in`: time handling | `datetime.fromtimestamp(ms / 1000)` and `datetime.now()` use the server's local zone (naive). `date` is the server-local date, not the IST date (R1). Overnight shifts are ignored. Sub-second parts are kept (R1 says truncate). `if body.punched_at` treats `0` as "not given". `punched_at` is not range-checked, so seconds (`1783312500`) or floats are accepted. | A punch at 00:30 IST gets the previous date when the server runs on UTC; `punched_at` in seconds gives a 1970 date. | `ms_to_dt` (exact, UTC), `attendance_date()` implements R1 incl. overnight, truncate to whole seconds, strict `EpochMs` type (int, >= 1e11, <= 4102444800000) -> 422. |
| 9 | `punch_in`: status and response | `status` is any string (`"ABSENT"`, `"banana"` accepted). The response adds `id` (the internal `_id`) and returns raw datetimes instead of epoch ms. | `{"status": "LEAVE"}` returns 201. | `status` is a `Literal["PRESENT","WFH","ON_DUTY"]`; response built by `record_out()` (no `id`, epoch ms). |
| 10 | `compute_late_minutes` | Builds the shift start with `punch_in.replace(hour=...)` in whatever zone the datetime has (not IST) and on the punch's own date (wrong for overnight shifts). `int(total_seconds()/60) > 10` fails the "strictly more than 10:00" rule: 09:40:01 gives `int(10.01)=10`, not `> 10`, so 0 instead of 10. | Shift 09:30, punch 09:40:01 -> expected 10, got 0. | `compute_late_minutes` works in whole seconds from the IST shift start on the *attendance date*: `secs > 600` -> `secs // 60`. |
| 11 | `compute_work_hours` | `round()` is banker's rounding on floats (R4 wants half-up): 3 h 0 m 18 s = 3.005 h gives 3.0, expected 3.01. No sub-second truncation. | Unit test on the 3.005 case. | `work_hours_hundredths()`: integer arithmetic, `half_up_div(secs*100, 3600)`. |
| 12 | `compute_overtime` | Mixes an aware `end` (IST) with a naive `punch_out` -> `TypeError`. Ignores the 30-minute minimum (R3) and overnight shifts (end is on the next day). | Any punch-out call, or `punch_out` 18:40 on a 18:30 shift (expected 0, returns 10). | `compute_overtime` uses aware datetimes, `mins >= 30` else 0, shift end on date+1 for overnight shifts. |
| 13 | `list_attendance` | Loads the whole collection into memory (`list(find(q))`), sorts in Python, slices in Python. Sort is only by `date` (contract: then `emp_code` asc). `page=0` gives a negative slice, no `page_size` cap, no date validation (`date_from > date_to` must be 422), unvalidated `status`. Leaks `_id` as `id`, returns raw datetimes, and legacy records without `history` / `half_day` are returned as they are. | 100k records: seconds and hundreds of MB per request. | Database-side `sort` + `skip` + `limit` backed by indexes, `count_documents(q)` for the total, validated parameters, `record_out()` with defaults for missing fields. |
| 14 | `list_attendance`: `date` filter | Dates are compared as strings without checking the format, so `date_from=2026-7-1` silently compares wrongly. | `?date_from=2026-7-1` returns wrong rows instead of 422. | Strict `YYYY-MM-DD` parsing (real calendar date) -> 422. |

**Looked at and decided it is fine**
- `load_dotenv()` with its default `override=False`: real environment variables already win over `.env`, as required.
- Sync (`def`) endpoints with PyMongo: FastAPI runs them in a thread pool, so concurrent requests are fine; the correctness problems were the check-then-write patterns, not threading.
- `{"_id": 0}` projection in `list_employees`: correct idea, kept (the `_id` must never be returned).
- Starting `MongoClient` at import time: it connects lazily, so the app still starts when MongoDB is slow; `/health` now reports readiness.
